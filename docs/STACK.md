# Задача 5. Мой вайбкод / LLM-стек

Пишу как есть, про свою реальную рабочую среду, а не «как правильно».

## 1. IDE и модели сейчас, и как это менялось за полгода

Сейчас у меня терминал вместо IDE. Основной инструмент Claude Code в tmux на своём VPS (Debian), туда же подключены MCP-серверы (браузер Playwright, Google Workspace, Firecrawl, Figma, Notion). Второй агент OpenAI Codex CLI, он у меня для независимого второго мнения: кросс-ревью кода и архитектуры, и как резерв, когда у Claude кончается недельная квота. Третий слой Hermes, open-source агент, который крутится под supervisor и делает фоновую работу по расписанию и из Telegram: мониторинг, бэкапы, парсеры, рассылки. У всех трёх общий набор скиллов в одном каталоге, чтобы не поддерживать три копии инструкций.

Полгода назад было иначе: VS Code с Copilot, ChatGPT в отдельной вкладке, Cursor попробовал и бросил, потому что он хорош для одного репозитория, а у меня десяток сервисов на сервере, systemd-юниты, cron, три машины по SSH. Агент, который живёт в терминале и сам ходит по SSH на другие узлы, оказался ближе к тому, как я реально работаю. Переломный момент был, когда я перестал писать промпт «сделай», а завёл для агента файл с законами проекта (что нельзя трогать, как рестартить сервисы, куда класть секреты) и память между сессиями. После этого качество выросло сильнее, чем от любой смены модели.

По моделям: основная сейчас Claude Fable 5.1 (до неё Opus 4.x, до неё Sonnet). Для дешёвых массовых задач Haiku 4.5: классификация тысяч карточек в парсере, персонализация в этом тестовом, память агента. Для Codex модели GPT-5 семейства по подписке ChatGPT. У Hermes цепочка запасных провайдеров (GLM, Qwen, DeepSeek, Gemini Flash по бесплатному ключу), потому что одна модель без фоллбэка в проде ложится в самый неподходящий момент. Локально в LM Studio живёт Qwen для голосового ассистента, где важна задержка, а не ум. Картинки и видео делаю на Vertex AI (Imagen, Veo) на кредитах Google, локальные модели снёс: облачные заметно сильнее.

## 2. Подписки

Платных подписок две: Claude (это ~80% всей моей работы, включая Claude Code и Haiku для батчей) и ChatGPT (ради Codex CLI и как второе мнение). Всё остальное живёт на бесплатных квотах и кредитах: Gemini и Groq по бесплатным ключам, DaData 10 000 запросов в день для ЕГРЮЛ, Tavily для поиска с бесплатным лимитом плюс свой SearXNG, кредиты Google Cloud на генерацию медиа. Плюс сам сервер. Отдельно API-ключ Anthropic я не покупаю: подписка выгоднее, пока укладываюсь в лимиты, а батчи считаю на Haiku. Итого мне хватает двух подписок и сервера, чтобы вести параллельно лидген, парсер соцсетей, три торговых бота, голосового ассистента и сайты клиентов. Когда квота Claude заканчивается раньше недели, это сигнал, что я гоняю тяжёлую модель на задачах, которым хватило бы Haiku.

## 3. Как сравниваю модели и инструменты

Только на одинаковом наборе задач. По ощущениям сравнивал в первые месяцы и каждый раз ошибался: новая модель кажется умнее просто потому, что ответила по-другому. Сейчас у меня есть маленький набор из 8–10 реальных задач из бэклога: починить конкретный баг с известным ответом, дописать функцию с тестами, разобрать лог инцидента, переписать письмо человеческим языком. Даю обеим моделям одинаковый бриф, одинаковый контекст, потом смотрю три вещи: сколько правок мне пришлось внести до рабочего состояния, сколько раз агент соврал про результат (сказал «готово», а тесты не запускал), и сколько токенов и минут ушло. Для текстов дополнительно гоняю через свой скрипт-детектор штампов машинного текста. Для торговых ботов отдельное правило: отчитываюсь только цифрами бэктеста движка, а не «модель посчитала, что стратегия лучше».

Отдельная привычка: параллельный прогон. Claude и Codex получают одну и ту же задачу независимо, потом сравниваю диффы. Часто выигрывает не тот, кто написал больше, а тот, кто нашёл в задаче ошибку в постановке.

## 4. Какие тесты потребую для новой функции

Для чистой логики юнит-тесты на нормальные входы, граничные и заведомо плохие (пустая строка, кириллица в домене, обфусцированный e-mail). Если функция чинит баг, сначала должен появиться падающий тест, который воспроизводит баг, потом код. Агент у меня работает по этому правилу жёстко: код без предшествующего красного теста удаляется и пишется заново. Для всего, что ходит в сеть или в LLM, один интеграционный тест на зафиксированных данных (сохранённый HTML страницы, сохранённый ответ модели) и один живой прогон с `--limit 3` на реальных данных перед тем, как поверить. Плюс проверка отрицательного результата: функция должна честно вернуть «не нашёл», а не пустую строку, которая потом уедет клиенту как факт. В этом тестовом это ровно проверка цитаты: модель обязана вернуть дословный кусок текста с сайта, и скрипт ищет его в скачанном тексте, иначе факт помечается как неподтверждённый.

И ещё одно, чему научился на своих же ошибках: тестировать надо тот путь, который реально исполняется в проде, а не механизм в вакууме. У меня был скрипт восстановления бэкапа, который печатал OK поверх семи тысяч расхождений, и учение прошло «успешно».

## 5. Какие разрешения дам coding-агенту с доступом к терминалу и базе

Читать можно почти всё, писать только в своём рабочем дереве. Конкретно:

- Отдельный системный пользователь без sudo. Никакого `NOPASSWD: ALL`, это у меня записано первым пунктом в правилах для всех агентов.
- База: отдельная учётка с правами только на чтение для аналитики. Запись в прод-таблицы только через миграции, которые я прочитал глазами. Любое массовое `UPDATE`/`DELETE` без `WHERE` и любые `DROP` вырезаны на уровне прав, а не промпта.
- Секреты не печатать и не коммитить: ключи лежат в `.env` вне репозитория с правами 600, pre-commit хук с gitleaks и своим сканером с перебором кодировок (однажды пароль в CP866 прошёл мимо gitleaks и обычного grep).
- Список действий, которые агент делает только по моей явной команде на этот конкретный запуск: рестарт прод-сервисов, обновления ядра и системных пакетов, `docker prune`, удаление бэкапов и снапшотов, переключение на платного провайдера, внешняя публикация и рассылка, запуск дорогих прогонов (парсер, лидген). Агент готовит команду и показывает, но не отправляет.
- Перед изменениями бэкап (backup-before), после них проверка живости, а не «процесс запустился». Сторож не имеет права написать «восстановлено», пока не проверил ответ сервиса.
- Ограничение по времени и объёму: bounded-задача, лог через `script`, чтобы потом можно было прочитать, что именно агент делал, а не его пересказ.

Причина такой конструкции простая: агент ошибается уверенно и на скорости, которой у человека нет. Поэтому границы должны стоять в правах и хуках, а не в вежливой просьбе в промпте.

## 6. Автотесты и CI/CD

Да, пишу, и агент пишет их за меня чаще, чем я сам. В этом репозитории это видно: `tests/` с pytest, `ruff` как линтер, GitHub Actions гоняет и то и другое на каждый push. Обязательный набор перед слиянием:

1. Линтер и форматирование без предупреждений.
2. Юнит-тесты зелёные, новый код покрыт хотя бы одним тестом на успех и одним на отказ.
3. Сканер секретов по staged-файлам (gitleaks + проверка, что все файлы UTF-8).
4. Аудит зависимостей (`pip-audit`), для внешних скиллов и SKILL.md дополнительно статический скан на prompt-injection.
5. Живой смоук на маленьком объёме реальных данных с фиксацией результата в отчёте, а не «прогнал, всё ок».

Перед деплоем: бэкап того, что меняем, деплой через один и тот же безопасный скрипт (не руками из истории bash), проверка здоровья сервиса по реальному пути (запрос, который делает пользователь), готовый откат. После деплоя коммит и пуш сразу, потому что я сам смотрю по GitHub, что было сделано, и незакоммиченная волна работы для меня как несуществующая.

Что не делаю: не гоняю в CI тесты, которым нужен живой LLM. Они нестабильные и платные. Ответы модели для тестов фиксируются файлами, а живой прогон один, руками, перед релизом.
